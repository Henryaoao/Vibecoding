# ProjectM OMX 决策策略

## 1. 目的

本文定义 OMX 代理在 ProjectM PRD 和实现任务中可以自行决定什么、必须继承什么，以及哪些事项必须向用户确认。

## 2. 优先级

使用 `docs/prd/README.md` 中的事实来源优先级。简化规则如下：

1. 用户当前明确指令优先。
2. 整体项目 PRD 是稳定产品基线。
3. 本文定义执行红线和确认策略。
4. 端侧 PRD 定义各端自己的范围。
5. 阶段 PRD 定义可执行切片。

## 3. 硬红线

代理不得自行改变以下内容：

- ProjectM 是公司内部多端门户。
- MVP 模块固定为七个：今日公司简报、公司公告墙、员工论坛热帖、新人专区、财经轻资讯、文档中心、培训中心。
- 应用角色只能是 `user` 和 `super_user`。
- 后端授权是事实来源。
- `/api/v1/admin/*` 必须要求 `super_user`。
- 不得重新引入 `content_admin`、`department_admin`、`system_admin`。
- 不得实现浏览历史、`recent_views`、页面访问轨迹或等价被动行为历史。
- 财经轻资讯不得包含股票推荐、买卖建议、个股预测或收益承诺。
- App 不包含移动端管理写入；所有 `super_user` 管理写入属于 Web Admin Console。

## 4. 必须用户确认的事项

以下事项需要先说明影响，再等待用户确认：

- 改变项目定位、目标用户、MVP 模块或角色模型。
- 调整七个 MVP 模块的边界、合并、拆分或新增模块。
- 改变 Web/App 端侧文档范围。
- 改变 `docs/prd/` 文档结构、事实来源优先级、阅读顺序、文件命名或阶段 PRD 层级。
- 放宽 `docs/agents/capability-governance.md` 中的角色修改权限、自我验证 gate 或交接规则。
- 改变 App 技术栈或加入 App 管理写入。
- 改变财经合规边界。
- 改变会影响生产部署、安全边界、数据保留或隐私合规的技术方案。
- 把测试用例、部署细节或具体 UI 文案上移到整体项目 PRD。

## 5. 已接受的端侧技术决策

- Web 技术栈：React + TypeScript + Vite。
- App 技术栈：React Native + TypeScript + Expo-managed workflow。
- 后端方向：Go REST API。
- 数据库方向：PostgreSQL 16。
- 本地运行方向：Docker Compose，包含 frontend、backend、PostgreSQL 和 pgAdmin。
- pgAdmin 默认端口：`5050`。
- App 管理边界：App 仅承载员工门户使用场景，所有 `super_user` 管理和写入工作流由 Web Admin Console 承担。

## 6. 代理可以自行决定的事项

在不触碰硬红线且不改变已确认技术基线的前提下，代理可以自行推进：

- 阶段 PRD 内部的章节组织和更清晰的验收标准。
- 模块数据库、后端、Web、App 四层之间的依赖排序。
- 不改变 API 事实的前端状态拆分。
- 不改变合规边界的错误状态、空状态和重试策略。
- 更利于 OMX 独立执行的文档拆分、链接和合同登记。

## 7. 跨层合同策略

| 层级 | 负责定义 | 不得定义 |
| --- | --- | --- |
| 数据库 PRD | 数据事实、约束、索引、生命周期、样例形态。 | 端侧 UI 行为。 |
| 后端 PRD | API 合同、授权、验证、生命周期、审计写入。 | 依赖前端隐藏作为安全边界。 |
| Web PRD | 浏览器体验、路由、页面状态、组件边界、API 消费。 | 重写后端权限或数据库事实。 |
| App PRD | 移动端信息架构、导航、平台状态、API 消费。 | 管理写入、后端权限事实或数据库事实。 |

## 8. 未写明事项处理

- 如果未写明事项会改变模块边界、角色、合规、端侧范围、技术栈或安全面，必须问用户。
- 如果未写明事项只是实现细节，代理应选择常规、可维护、可测试的方案，并在交接或提交信息中记录理由。
- 如果出现 PRD 冲突，先按事实来源优先级解决；仍无法解决时问用户。
