# ProjectM 整体项目 PRD

## 1. 文档状态

- 状态：ProjectM 稳定项目宪章。
- 适用范围：所有 Web、App、后端、数据库和 OMX 执行工作。
- 变更规则：项目定位、目标用户、MVP 模块、角色权限和合规边界不得由代理自行改变；如需改变必须先向用户确认。

## 2. 产品定位

ProjectM 是一个面向公司内部员工的多端门户。它的目标是把公司信息、公告、内部讨论、新人引导、财经轻阅读、文档和培训集中到一个可信入口，让员工更容易获取信息，让运营人员更容易维护内容。

ProjectM 不是公开营销站点、消费者社区、交易工具或通用内容管理平台。产品优先优化内部信息触达、权限清晰、内容运营可控、审计可追溯和后续 OMX 可管理交付。

## 3. 目标用户

| 角色代码 | 产品用户 | 主要目标 | 边界 |
| --- | --- | --- | --- |
| `user` | 公司员工 | 获取公司信息、阅读公告、浏览热帖、完成新人/培训任务、查找文档。 | 只能访问员工门户中自己有权限的内容；不能访问管理控制台和管理 API。 |
| `super_user` | 内部运营/管理员 | 管理门户内容、文档、课程、新人材料、用户、角色、首页配置和审计可见性。 | 可使用员工门户和 Web Admin Console；所有受保护操作仍必须由后端授权。 |

## 4. 产品目标

1. 为员工提供统一的内部信息入口。
2. 让七个 MVP 模块在 Web 与 App 中共享同一产品事实和后端合同。
3. 让 `super_user` 通过受控的 Web Admin Console 进行内容和管理工作。
4. 保持权限、内容可见性、审计、财经合规和隐私边界在各技术层一致。
5. 让后续 OMX 阶段工作可以按小 PRD 独立规划、执行和验收。

## 5. MVP 成功标准

ProjectM MVP 达成时应满足：

- 七个 MVP 模块均有员工可用的读取或互动入口。
- `super_user` 能在 Web Admin Console 完成必要的内容/管理写入。
- 后端授权能阻止未授权管理 API 调用，而不只依赖前端隐藏入口。
- Web 与 App 端消费同一后端合同，不各自发明权限事实。
- 财经轻资讯不包含股票推荐、买卖建议、个股预测或收益承诺。
- PRD 层级清晰，OMX 能从阶段 PRD 进入实现而不需要重新拆解大文档。

## 6. MVP 模块清单

| 模块 | 目的 | 员工能力 | 管理能力 |
| --- | --- | --- | --- |
| 今日公司简报 | 汇总当天公司重点信息。 | 查看当日简报和历史简报。 | 创建、编辑、排期、发布、置顶、归档和下线简报。 |
| 公司公告墙 | 发布正式公告和通知。 | 查看、筛选、搜索公告。 | 创建、编辑、置顶、设置有效期、发布、归档和下线公告。 |
| 员工论坛热帖 | 聚合内部讨论热点。 | 查看热帖、详情和允许的轻量互动。 | 管理热帖可见性、状态、排序和治理动作。 |
| 新人专区 | 提供入职资料和任务。 | 查看新人资料、更新自己的入职任务状态。 | 维护入职资料、任务模板、排序和状态。 |
| 财经轻资讯 | 提供宏观、行业和金融知识类轻阅读。 | 阅读资讯并看到非投资建议提示。 | 发布、编辑、归档、下线和合规检查内容。 |
| 文档中心 | 集中管理内部制度、模板和常用文件。 | 搜索、筛选、查看并下载有权限文档。 | 上传、编辑、授权、发布、归档和下线文档。 |
| 培训中心 | 提供课程、材料和个人学习进度。 | 浏览课程、查看材料、更新自己的学习进度。 | 创建、编辑、发布、归档、下线课程和材料。 |

## 7. 角色与权限基线

### 7.1 固定角色

ProjectM 只有两个应用角色：`user` 与 `super_user`。

不得重新引入 `content_admin`、`department_admin`、`system_admin` 或任何第三种应用角色。未来如需更复杂的组织权限，应先作为新需求向用户确认。

### 7.2 授权原则

- 后端授权是受保护行为的事实来源。
- 前端角色隐藏只能改善体验，不能作为安全边界。
- `/api/v1/admin/*` 必须要求 `super_user`。
- `user` 不得访问 Admin Console 能力或管理 API。
- 管理写入应可归因、可审计，但不得记录密钥或敏感正文载荷。
- 用户操作归因应记录 ProjectM 内部 `users.user_id`，建议审计字段名为 `actor_user_id`；Teams 登录只提供外部身份映射，跨租户辨别使用 `teams_tenant_id` + `teams_user_id`，不得以邮箱或显示名作为稳定审计标识。

### 7.3 Admin Console

Admin Console 仅面向 `super_user`。它覆盖内容管理、文档管理、培训管理、新人管理、用户与角色管理、首页配置、分类/标签管理和审计查看。

当前端侧基线中，Admin Console 管理和管理写入工作属于 Web。App 可以让 `super_user` 作为员工门户用户使用，但不包含移动端管理写入，除非未来用户明确改变该边界。

## 8. 合规与隐私边界

- 财经轻资讯必须定位为轻阅读和知识信息，不得提供股票推荐、买卖建议、个股预测或收益承诺。
- 不得实现浏览历史、`recent_views`、页面访问轨迹或等价的被动用户行为历史，除非用户未来明确反转该决策。
- 文档下载、管理写入、角色变更等必要业务审计可以设计，但必须限制用途并避免收集无关行为数据。
- 认证、授权、审计、内容生命周期和数据保留策略应在阶段 PRD 或实现方案中细化。

## 9. 高层产品结构

ProjectM 有两个高层产品面：

1. 员工门户：`user` 与 `super_user` 都可使用，用于读取信息、参与允许的轻量互动、查看文档和完成个人任务。
2. Admin Console：仅 `super_user` 可访问，用于内容和管理工作。

Web 与 App 必须继承同一产品基线、模块清单、角色规则和合规边界。端侧文档可以选择不同的信息架构、交互模式和技术栈，但不得重写共享产品规则。

## 10. 交付阶段顺序

ProjectM 建议从稳定基础到模块切片交付：

1. 产品与文档基础：整体 PRD、端侧 PRD、权限参考、决策策略和阶段 PRD 结构。
2. 应用基础：项目脚手架、认证会话、通用 API 合同、后端授权基础、Web 壳层、App 壳层。
3. 模块数据库层：七个 MVP 模块的数据事实、生命周期、约束和样例数据对齐。
4. 模块后端层：七个 MVP 模块的员工接口、管理接口、授权、验证和审计。
5. 模块端侧层：Web 与 App 模块体验分别消费后端合同。
6. 集成与验收：端到端串联、权限验证、合规验证和 QA 计划。

## 12. 本整体 PRD 不包含

- 完整测试用例、测试脚本或自动化 QA 设计。
- 具体 UI 文案、颜色、像素级设计和组件实现细节。
- 具体部署步骤、云资源、CI/CD 密钥或生产运维方案。
- API 字段清单、数据库字段清单或迁移 SQL。
- 某个端的全部页面细节。
- App 行为作为 Web 行为的派生说明。

## 13. OMX 执行原则

- 执行前先确认当前任务属于基础阶段、模块数据库层、模块后端层、Web 前端层还是 App 前端层。
- 优先读取对应阶段 PRD，不要从整体 PRD 推断具体字段或 UI 文案。
- 如阶段 PRD 没写清楚且会影响模块边界、角色、合规、端侧范围或技术栈，必须向用户确认。
- 如只是实现细节且不改变上述边界，代理可以提出推荐方案并记录理由。
