# Anti-Overfit Guards

Use these guards before promoting any learning.

## 1. Ban Raw Incident Promotion

Do not promote:

- one route
- one wording choice
- one UI quirk
- one team habit
- one named project, customer, repository, ticket, environment, or internal system

## 2. Prefer Diversity

A candidate is stronger when it appears across:

- different products
- different task types
- different document classes
- different categories

## 3. Collapse Narrow Variants

If three narrow lessons are really one broader principle, promote the broader principle instead of all three narrow variants.

## 4. Require a Thinking Habit

If the lesson cannot be rewritten as:

- an audit question
- a verification habit
- a decision rule

it is still too narrow.

## 5. No-Change Is Valid

A case may be informative without justifying a global rule change.

## 6. White-Label Cross-Project Skill Evolution

For skills intended to work across projects, evolution records must be white-labeled before they are written, reviewed, or promoted.

Do not preserve project-specific identifiers in `source_task`, `summary`, `action`, `failure_mode`, `pattern_key`, `principle_key`, `principle`, release notes, or human-readable memory.

Remove or generalize:

- project names
- customer names
- internal system names
- repository names
- issue or ticket names
- real environment names
- proprietary module names that only make sense in one project

Use reusable category names instead, for example:

- `credentialed-admin-report-evidence-repair`
- `high-risk-prd-branch-completeness-audit`
- `testcase-status-normalization-fix`
- `runtime-inbox-overlay-install-handoff`

Project-specific details may stay in the original project workspace, private notes, or a project-specific skill. They must not become part of a shared cross-project skill's canonical evolution history or inbox records.
